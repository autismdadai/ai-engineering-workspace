## 5. Answers to the 11 questions

### Q1. ReAct's action format; JSON schemas; how today's tool APIs define tools
Takeaway: ReAct used free-text actions in few-shot prompts and no JSON schemas. JSON Schema is how Anthropic and OpenAI define tools today.
- HotpotQA and FEVER actions: search[entity] (returns the first 5 sentences of that entity's Wikipedia page), lookup[string] (find a string in the page) and finish[answer] (Sec. 3.1). ALFWorld uses text commands such as go to, take and use; WebShop uses search, click and think style actions (Sec. 4, Table 6). The question writes the names capitalised; the fetch summary reported them in lower case. [ReAct, arXiv:2210.03629v3, ICLR 2023](https://arxiv.org/pdf/2210.03629) (preprint copy)
- Prompting: few-shot, human-written trajectories of thoughts, actions and observations; 6 randomly chosen cases for HotpotQA and 3 for FEVER (Sec. 3.2); ALFWorld uses 3 annotated trajectories per task type and WebShop is one-shot; main model PaLM-540B, with GPT-3 text-davinci-002 results in Appx A.1 (Table 5). Same source.
- JSON: the fetch summary found no mention of JSON, JSON Schema or function calling anywhere in the paper. That is summary-based; I did not search the PDF text myself.
- Anthropic: a tool is a name, a description and an input_schema that is a JSON Schema object, and the API builds a special system prompt from the tool definitions. [Define tools](https://platform.claude.com/docs/en/agents-and-tools/tool-use/implement-tool-use) (official docs, no date shown)
- OpenAI: function tools carry type, name, description, a parameters JSON Schema and optional strict; definitions are injected into the system message and count as input tokens. [Function calling](https://developers.openai.com/api/docs/guides/function-calling) (official docs, no date shown)
- Gap: the ICLR conference page was not opened; the arXiv copy's footer says it was published at ICLR 2023.

### Q2. Returning tool errors to the model

### Q4. gVisor: what the official docs say
Takeaway: gVisor is a Go application kernel (the Sentry) with a Gofer helper and a pluggable syscall-interception platform. Systrap is the default, ptrace is unsupported, the gofer protocol is LISAFS and directfs is the default; the docs describe risk reduction, not a guarantee.
- What it is: an application kernel with a Linux-like interface, written in Go and running in userspace, with an OCI runtime called runsc; the Sentry is the largest component and does not pass application syscalls to the host kernel, though it makes some host syscalls of its own. [What is gVisor?](https://gvisor.dev/docs/) (official docs)
- Platforms: systrap (seccomp SECCOMP_RET_TRAP, SIGSYS) is the default, replacing ptrace in mid-2023; ptrace is no longer supported and expected to be removed; KVM runs the Sentry as guest OS and VMM and suits bare metal. [Platform Guide](https://gvisor.dev/docs/architecture_guide/platforms/) (official docs). Default in source code: could not check (budget).
- Gofer and file protocol: the docs intro still describes 9P between Gofer and Sentry, which is stale. The 27 Jun 2023 post says runsc's gofer protocol is now LISAFS and directfs is the default; Edera (updated 2026-03-07) says current versions default to directfs. [directfs post](https://gvisor.dev/blog/2023/06/27/directfs/) (vendor blog) ; [Edera](https://docs.edera.dev/technical-overview/concepts/edera-vs-gvisor/) (vendor comparison)
- directfs: the Sentry accesses container files directly, using fd-relative syscalls on descriptors the gofer hands over (SCM_RIGHTS), instead of round trips to the gofer. The trade-off is that the sandbox gets the gofer's privileges (CAP_DAC_OVERRIDE, CAP_DAC_READ_SEARCH) and relies less on seccomp filters. The post reports stat(2) more than 2x faster and 12% less absolute time on real workloads (systrap, bind mounts; version and hardware not given; the author says not to extrapolate).
- Security model: aims to limit the host's exposed system API through layers (the Sentry intercepts, and its own reach to the host is kept small) with continuous fuzzing; it does not protect against hardware side channels, relies on the host and platform for hardware attacks, and says a sandbox is no substitute for a secure architecture. [Security model](https://gvisor.dev/docs/architecture_guide/security/) (official docs)
- Performance: no emulation of CPU instructions and no extra cost on raw memory access; the cost lands on syscall-bound workloads (high-performance data stores, static network services), small-file serving and some network paths; memory overhead is a small, mostly fixed amount. Benchmarks are from GCE n1-standard-4 (Broadwell), Debian 9, kernel 4.19, mostly ptrace, with no version or date. The intro page adds reduced application compatibility. [Performance Guide](https://gvisor.dev/docs/architecture_guide/performance/) (official docs)
- Install: either the apt repository (project GPG key, signed-by source list, apt-get install runsc, which configures Docker automatically if present) or the release tarball with a published sha512 file checked via sha512sum -c; x86_64 and ARM64; the page states Linux 5.6 or newer. Only the apt route is described as GPG-signed; tarball verification is checksum only. [Install](https://gvisor.dev/docs/user_guide/install/) (official docs). See the page's auto-download deadline in section 3.
- Docker runtime: sudo runsc install, restart Docker, docker run --runtime=runsc (Docker 17.09.0 or later); dmesg shows gVisor's simulated boot log but must not be used as a security check; debug options include --strace. [Docker quick start](https://gvisor.dev/docs/user_guide/quick_start/docker/) (official docs)

### Q5. Firecracker: stated boot time and memory overhead; is "heavy" fair?
Takeaway: Firecracker's own site claims boot in under 125 ms and under 5 MiB overhead per microVM, so "heavy boot times and memory overhead" is not supported by its own numbers. - Site claims: boot under 125 ms; under 5 MiB overhead per VM; up to 150 microVMs created per second per host. Firecracker is a KVM-based VMM written in Rust, built at AWS, with a minimal device model (5 emulated devices per its FAQ) and a companion "jailer" process as a second line of defence. No hardware, guest or configuration is given for the figures. [Firecracker](https://firecracker-microvm.github.io/) (official site, vendor claims)

- Fairness: "full VMs like Firecracker" is also loose, since Firecracker is a stripped-down microVM monitor. A real trade-off remains: gVisor pays in syscall and I/O speed and compatibility (its own docs), while a microVM carries a guest kernel per VM (my inference, not measured here).
