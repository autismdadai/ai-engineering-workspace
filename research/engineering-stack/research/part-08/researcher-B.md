## (b) Ledger rows settled (P7-02 to P7-09, P7-11)

- **P7-02 (isolation is a "mandatory security primitive"): overstated, stays.** No opened source says "mandatory". gVisor: "*A sandbox is not a substitute for a secure architecture*" (B36). The tools themselves don't make it mandatory: Claude Code's sandbox "is off by default" (B55), Gemini CLI's is "disabled by default" (B69), and Claude Code falls back to running unsandboxed if the sandbox can't start (B59). Reasonable wording: isolating untrusted code is strongly recommended and reduces risk. Don't call it mandatory.
- **P7-03 (application kernel in Go that intercepts syscalls): confirmed.** It runs in user space and ships runsc (B26, B29).
- **P7-04 (shared host kernel, "massive attack surface"): overstated, stays.** The shared kernel is confirmed (B01, B28: gVisor says a workload is "only one system call away from host compromise"). Neither gVisor nor Docker docs put a number on the surface or call it "massive". Docker says default containers are "quite secure" (B09) but admits "incomplete isolation ... in combination with kernel vulnerabilities" (B08), and its seccomp profile blocks "around 44 system calls out of 300+" (B10). The runc CVEs (B51 to B54) are real escapes, but they are runtime bugs, not kernel attack surface.
- **P7-05 (Sentry intercepts via seccomp/systrap or KVM): confirmed.** systrap is the default (flag default `"systrap"`, B30). "replaced `ptrace` ... in mid-2023"; ptrace "is no longer supported" (B31). One caveat: the performance page charts still show `runsc-ptrace` (B38).
- **P7-06 (Gofer over 9P or directfs): outdated, stays, with exact evidence.** filesystem.md: "using the LISAFS protocol"; "Directfs is enabled by default in runsc"; the flag help says "Sentry runs with higher privileges" (B32). The overview page at gvisor.dev/docs/ still says "via the 9P protocol" (B33), so the paper's error has a source in gVisor's own docs.
- **P7-07 (gVisor vs Firecracker): overstated, stays, but correct the ledger note.** The ledger says Firecracker's figures have "no test conditions". That's wrong for SPECIFICATION.md, which states them: M5D.metal or M6G.metal, 1 vCPU and 128 MiB, minimal kernel, serial console off, measured from the InstanceStart call to `/sbin/init`, `<= 125 ms` and `<= 5 MiB` VMM overhead, checked by integration tests (B45). The website drops these conditions (B46). They're still vendor figures. gVisor's costs are per-syscall and fall mostly on "system call bound" applications (B38). Neither is lighter on every measure. Firecracker also needs the jailer and host-level egress filtering (B47, B48).
- **P7-08 (tools: Pytest, Docker, gVisor runsc, custom runners): confirmed.** pytest 9.1.1 exists on PyPI (wheel downloaded, MIT). The gVisor tag release-20261005.0 exists (cloned). runsc installs as a Docker runtime named "runsc" (B40). Docker Engine 29.9.1 is current (B24).
- **P7-09 (gVisor "ensures" safety): overstated, stays.** "We cannot guarantee that a container escape will never happen in gVisor" (B37, VB 2020). Its defense-in-depth principles (security.md L179-197) aim to cut risk, and it gives no protection against hardware side channels (B35). It also doesn't protect what the sandbox is configured to reach, or higher layers such as containerd (B35).
- **P7-11 ("standard Docker is insufficient"; runsc procedure): split verdict, and the ledger note needs one correction.** The procedure is confirmed (B40, B41): `sudo runsc install`, restart Docker (quick start: `sudo systemctl restart docker`; install page: `reload`), `docker run --runtime=runsc`, with `--strace` in `runtimeArgs` and logs in the `.boot` file. The ledger says "No opened source says plain Docker is insufficient". gVisor's README does come close: running untrusted code in containers "without additional isolation is not a good idea" (B27). That source has a stake in the answer, though. Docker calls its defaults "quite secure" (B09), and smolagents calls Docker "truly robust" isolation (B78). Suggested wording: "gVisor's maintainers advise extra isolation beyond plain containers for untrusted code; Docker's own docs call default containers quite secure, so this is a judgment, not a settled fact."

## (c) Hardened `docker run` for untrusted agent code

```bash
docker run --rm \
  --network none \
  --cap-drop ALL \
  --security-opt no-new-privileges \
  --read-only \
  --tmpfs /tmp:rw,noexec,nosuid,size=64m \
  --pids-limit 128 \
  --memory 512m --memory-swap 512m \
  --cpus 1 \
  --user 65534:65534 \
  -v "$PWD/task:/work:ro" -w /work \
  python:3.12-slim python /work/main.py
# Stronger kernel boundary, Linux only, after `sudo runsc install` and a Docker restart:
#   add  --runtime=runsc
```

Untested here (there is no Docker daemon in this environment). The image tag and numbers are examples to adjust.

| Flag | What it does | Source |
|---|---|---|
| `--rm` | Deletes the container when it exits | run reference (not quoted here; standard flag) |
| `--network none` | "only the loopback device is created" | B17 |
| `--cap-drop ALL` | Drops even the 14 default capabilities; Docker's advice is "remove all capabilities except those explicitly required" | B06, B07 |
| `--security-opt no-new-privileges` | `su`/`sudo` and setuid gains "no longer work" | B18 |
| `--read-only` | Root filesystem read-only, "prohibiting writes to locations other than the specified volumes" | B15 |
| `--tmpfs /tmp:rw,noexec,nosuid,size=64m` | A small scratch area that can't hold executables or setuid binaries and has a size cap | B16 |
| `--pids-limit 128` | Caps processes (stops fork bombs) | B19 |
| `--memory 512m --memory-swap 512m` | Memory cap with no swap | B20, B21 |
| `--cpus 1` | At most one CPU's worth of time | B20 |
| `--user 65534:65534` | Runs as a non-root user (nobody); Docker's "Conclusions" stress non-privileged users | B09, run reference option `user` |
| `-v ...:ro` | Task files are read-only | run reference (volumes); B15 |
| No `--privileged`, no `-v /var/run/docker.sock` | `--privileged` "is not a securely sandboxed process"; socket access means "root-level privileges" | B14, B05 |
| Default seccomp profile left in place | "It is not recommended to change the default `seccomp` profile" | B13 |
| `--runtime=runsc` (optional) | Syscalls are handled by gVisor's Sentry instead of the host kernel | B29, B40 |

What it does NOT protect against:
- **Host kernel bugs.** Without runsc, the container still shares the host kernel: "only one system call away from host compromise" (B28). Seccomp and dropped capabilities shrink this, but Docker itself says isolation can be incomplete "in combination with kernel vulnerabilities" (B08).
- **Container runtime bugs.** runc escapes have happened repeatedly, including through a malicious image (B51 to B54). Patch runc and Docker. As written, the command runs the code as a non-root user, which the 2019 exploit required (root in the container).
- **Hardware side channels** (Spectre-style). Neither containers nor gVisor stop them (B35).
- **Misuse of what you mount.** Anything mounted can be read, and writable mounts can be changed. gVisor's note applies: the attacker "will still have access to whatever the sandbox is configured to have access to" (B35).
- **Disk use outside tmpfs.** Writable volumes, if you add any, have no size cap from these flags. Bind-mounting a writable host path is not covered.
- **Data exfiltration if you later turn the network on.** Allowlists filter by hostname, and domain fronting can get around them (B60). Firecracker likewise leaves egress filtering to the host (B48).
- **A compromised Docker daemon or socket.** Anyone who can reach the socket has root (B05).
- **Wrong verification.** Don't use `dmesg` inside the container to prove you're running under gVisor (B42).
- **Logic-level harm.** Bad output, wrong answers or prompt injection that steers what the code does with its legitimate inputs.
