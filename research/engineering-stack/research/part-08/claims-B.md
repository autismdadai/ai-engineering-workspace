## Claims

B001. [3.8 Stronger boundaries: gVisor and Firecracker] Unlike Linux, it is written in a memory-safe language (Go) and runs in userspace", and ships the container runtime `runsc` .  SOURCES: GVI
B002. [3.8 Stronger boundaries: gVisor and Firecracker] Its argument: with only seccomp and namespaces, "the workload is only one system call away from host compromise"; under gVisor, an attacker "would need to simultaneously exploit the gVisor Sentry kernel *and* the host Linux kernel, which do not share any code" .  SOURCES: GVI
B003. [3.8 Stronger boundaries: gVisor and Firecracker] - **Platforms.** "There are currently two supported platforms: 'Systrap' (the default)... 'KVM'". systrap "replaced `ptrace` as the default gVisor platform in mid-2023", and ptrace "is no longer supported" .  SOURCES: GVI, GVP
B004. [3.8 Stronger boundaries: gVisor and Firecracker] - **File access.** "Gofer instances communicate with their respective sentry using the LISAFS protocol", and "Directfs is enabled by default in runsc" . gVisor's overview page still says "the 9P protocol" , which is where the report's outdated claim (ledger P7-06) comes from.  SOURCES: GVF, GVO
B005. [3.8 Stronger boundaries: gVisor and Firecracker] - **No guarantee.** "*A sandbox is not a substitute for a secure architecture*" ; "We cannot guarantee that a container escape will never happen in gVisor" ; and "gVisor does not provide protection against hardware side channels" .  SOURCES: GVB, GVI, GVS
B006. [3.8 Stronger boundaries: gVisor and Firecracker] - **Cost.** Every system call costs more, which "will principally impact applications that are system call bound" .  SOURCES: GVM
B007. [3.8 Stronger boundaries: gVisor and Firecracker] To use it with Docker: `sudo runsc install`, restart Docker (`sudo systemctl restart docker`), then `docker run --runtime=runsc` ; `--strace` in its runtime arguments logs each system call to a `.boot` file .  SOURCES: GVD, GVQ
B008. [3.8 Stronger boundaries: gVisor and Firecracker] Don't check for gVisor by reading `dmesg` inside the container: that "is easily replicated by an attacker" .  SOURCES: GVQ
B009. [3.8 Stronger boundaries: gVisor and Firecracker] **Is plain Docker enough for untrusted code?** The sources disagree, so this part reports both views (ledger P7-11). gVisor's maintainers: "Containers are not a sandbox. ... using them to run untrusted or potentially malicious code without additional isolation is not a good idea" .  SOURCES: GVR
B010. [3.8 Stronger boundaries: gVisor and Firecracker] Docker: default containers are "quite secure" .  SOURCES: DSE
B011. [3.8 Stronger boundaries: gVisor and Firecracker] **Firecracker** is "a virtual machine monitor (VMM) that uses the Linux Kernel Virtual Machine (KVM) to create and run microVMs", built at AWS for Lambda and Fargate .  SOURCES: FCR
B012. [3.8 Stronger boundaries: gVisor and Firecracker] Its specification gives figures with their conditions (ledger P7-07): it "takes `<= 125 ms`" from the start call to the guest's first process, with VMM memory overhead "`<= 5 MiB`", measured on M5D.metal and M6G.metal hosts with a 1-vCPU, 128 MiB microVM, a minimal kernel and the serial console off, and "enforced by integration tests" .  SOURCES: FCS
B013. [3.8 Stronger boundaries: gVisor and Firecracker] The website drops the conditions .  SOURCES: FCW
B014. [3.8 Stronger boundaries: gVisor and Firecracker] In production, "Firecracker should be started only via the `jailer` binary", and since "Firecracker does not perform any network traffic filtering", outgoing traffic must be filtered on the host .  SOURCES: FCD
B015. [3.8 Stronger boundaries: gVisor and Firecracker] Neither is lighter on every measure: gVisor adds a cost to each system call, while Firecracker runs a whole guest kernel per sandbox .  SOURCES: FCS, GVM
B016. [3.8 Stronger boundaries: gVisor and Firecracker] E2B runs "One Firecracker microVM per sandbox" and needs an API key (Hobby plan free with a "$100 one-time usage credit", Pro $150 a month, October 14, 2026) .  SOURCES: E2B, E2P
